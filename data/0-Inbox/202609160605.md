# Job posting rewrite (markdown)

The empty [Untitled](/Users/greg/Code/Local/erp/Untitled) workspace will hold a **skills profile** plus a **rewrite playbook**. You paste a posting; the rewrite is a markdown file compared against your skills, ordered for a fit decision (skills first, company last).

## Files

- [`skills.md`](skills.md) — your maintained list. Group skills so matching is unambiguous (languages, frameworks, infra, domain, leadership). Each line is a skill you actually have; optional notes for depth (`production`, `side project`, `rusty`).
- [`job-rewrite.md`](job-rewrite.md) — instructions + output skeleton. This is the single source of truth for how every posting is rewritten.

Do not build an app. The workflow is: keep `skills.md` current → paste a posting (or URL + text) → produce `jobs/<company>-<role>.md` from the playbook.

## Rewrite output order

Every rewritten posting uses this heading order:

1. **Header** — role title, company, location/remote, compensation/level if stated. One-line **fit snapshot** (`N/M required skills match`, plus 1 sentence on the biggest gap).
2. **Required skills** (top of substance)
   - **Match** — posting requirement + which item in `skills.md` it maps to (include partial matches: e.g. “React listed, you have Svelte/frontend”).
   - **Gap** — required but not in `skills.md`. Flag must-haves vs. likely learnable.
   - If the posting mixes required vs. nice-to-have, keep those separate; only **required** drives the snapshot count.
3. **What I will need to do** — bullets of actual work (product, stack, ownership, on-call, travel, management). Strip mission fluff. Call out implicit work (e.g. “build hiring process” if founding engineer).
4. **Interview process** — stages, take-home, timeline if present. If missing, write `Not stated` and list what is still unknown.
5. **About the company** (last) — stage, product, size, funding, culture claims — only after the job itself is clear.

Optional short footer (after company, still last): **Unknowns / red flags** pulled from the posting (visa, unpaid take-home, “unlimited PTO” only, etc.).

## Matching rules (in `job-rewrite.md`)

- Compare posting requirements to [`skills.md`](skills.md) only; do not invent skills.
- Prefer conservative matching: related experience is a **partial match** in Match, not a full check.
- Ignore company-brand adjectives when extracting skills (`passionate about Kubernetes` still counts as Kubernetes if it is a requirement).
- Preserve source facts; do not hallucinate interview steps or compensation.

```markdown
# Staff Engineer — Acme

## Required skills

### Gap

## What I will need to do

## Interview process

## About the company
- ...
```

## What This Means for Your Strategy

**My recommendation flips at your volume**: skip the cheap models entirely and use **Claude Haiku** (or even Sonnet for borderline cases).

Here's why:

1. **The "savings" are meaningless.** Choosing Groq over Haiku saves you ~$5/year. One missed qualified job (or one wasted evening applying to a poor fit) costs you far more than that.
2. **Quality > cost at low volume.** At 100 jobs/week, false negatives (Haiku missing a match) are your real expense. Better reasoning per call is worth 6x the token price.
3. **No batch API needed.** Batch's 50% discount is pointless when you're saving fractions of a cent. Process in real-time, see results instantly.
4. **Room for a two-pass pipeline.** You could afford: Haiku for the initial filter on all 100 jobs (~$0.12), then Sonnet deep-analysis on the ~~10 borderline ones (~~$0.045). Total: **~$0.17/week** for excellent results.
