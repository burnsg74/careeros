# Haiku Job Fit Scoring in wellfound-capture.ts

## Decisions locked in

- Scoring runs inline in [playwright/scripts/wellfound-capture.ts](playwright/scripts/wellfound-capture.ts), between building the markdown and writing the file.
- The report is inserted above the job details, directly under the `[Wellfound](url)` link.
- A `SKIP` recommendation sets `status: deleted`, `deleted_auto: true`, and a mapped `deleted_reason`, matching the convention in [backend/src/lib/jobs.ts](backend/src/lib/jobs.ts) (lines 287-290).
- The prompt keeps `currency: "USD"` as-is; salary numbers are compared raw against the USD thresholds.
- Old notes in `~/Notebooks/CareerOS/4-Jobs/` will be deleted before the first run, so no backfill or migration path is needed.

## Prompt source

The prompt already exists at `~/Notebooks/CareerOS/8-Prompts/evaluate-job-fit.md` (161 lines). Read it at runtime and split on the `# USER TURN TEMPLATE` heading rather than duplicating it into TypeScript, so the vault stays the single source of truth:

- system = everything before that heading (`# ROLE` through `# OUTPUT SCHEMA`), 10,244 chars / ~2,900 tokens, which clears Haiku 3.5's 2,048-token minimum cacheable prefix so `cache_control` will actually engage.
- user = the text after the heading with `{{POSTING_MARKDOWN}}` replaced by the generated note markdown.

Fail loudly at startup if the file is missing or the heading is absent, before Chrome launches.

## New file: playwright/scripts/jobFit.ts

Three concerns, kept separate and pure where possible.

### 1. API call

```ts
const response = await client.messages.create({
  model: 'claude-3-5-haiku-latest',
  temperature: 0,
  max_tokens: 2048,
  system: [{ type: 'text', text: systemPrompt, cache_control: { type: 'ephemeral' } }],
  messages: [
    { role: 'user', content: userTurn },
    { role: 'assistant', content: '{' },
  ],
})
```

Prepend `{` to the returned text before `JSON.parse`. The prefill must have no trailing whitespace or the API rejects it.

On parse or schema-validation failure, retry once by continuing the conversation: `[user, assistant('{' + badText), user('Your previous response was not valid JSON. Return only the JSON object.'), assistant('{')]`. Transport errors (429/529/overloaded) are left to the SDK's built-in backoff with `maxRetries: 3`.

### 2. Schema validation

Use `zod` to mirror the `# OUTPUT SCHEMA` block exactly, with `.strict()` on every object so extra keys are a validation failure per the spec. This is ~40 fields with closed enums; hand-rolling it the way `parseJobStatusPatch` does would be ~150 lines of noise.

### 3. Math (model computes none of this)

Pure functions over the validated JSON:

- `nonSoft = skills.filter(s => !s.soft)`, `weight = HAVE→1, TOUCHED→0.5, DONT_HAVE→0`
- `requiredMatchPct` over `nonSoft` where `requirement === 'required'`; `overallMatchPct` over all `nonSoft`
- Divide-by-zero guard: if there are no required non-soft skills, fall back to `overallMatchPct`; if there are no non-soft skills at all, both are `0` (a posting listing no real tech is correctly a SKIP)
- `skills70Pass = requiredMatchPct >= 0.70`
- `primaryStackPass`: match each `primaryStack` entry to a `skills[]` entry by lowercased/whitespace-collapsed name; pass when tier-4 matches are fewer than half the entries. Unmatched entries count as not-tier-4; an empty `primaryStack` passes.
- `hardScreenFail = any hardScreen.*.result === 'fail' || !skills70Pass || !primaryStackPass`
- Score when `hardScreenFail`, made deterministic inside the spec's 0-2 band: `0` if any hard criterion failed, `1` if `!skills70Pass`, else `2`
- Otherwise base 9/8/7/5/3 by `requiredMatchPct`, then the five cumulative adjustments clamped to 0-10. Note the `.60-.69` and `<.60` branches are unreachable once `skills70Pass` holds; keep them so the table matches the spec.
- `annualizedMax`: `hour → ×2080`, `month → ×12`, `year → as-is`, `null` when `salaryMax` or `salaryPeriod` is missing (which also suppresses the `>= 100000` bonus). `hourlyEquivalent = annualizedMax / 2080`.
- Recommendation: `hardScreenFail → SKIP`; else `>= 9 && no 'unclear' → STRONG_PASS`; `>= 7 → PASS`; `>= 5 → HOLD`; else `SKIP`.

## Changes to wellfound-capture.ts

In `captureJobDetails`, after `toMarkdown(...)` and before `enqueueWriteText(mdPath, ...)`:

1. Score the generated markdown.
2. Merge `fit_*` keys into the frontmatter and splice the report in below the `[Wellfound](url)` line.

`toMarkdown` gets an optional evaluation argument rather than a second post-processing pass over the string, so frontmatter stays built in one place with the existing `yamlScalar` helper.

New frontmatter keys, matching the existing snake_case style:

```
fit_score: 7
fit_recommendation: PASS
fit_required_match: 0.83
fit_overall_match: 0.75
fit_primary_stack: React, Node.js, PostgreSQL
fit_missing_skills: Go, Kubernetes
fit_early_exit: false
fit_model: claude-3-5-haiku-latest
fit_evaluated_at: 2026-09-16T...
```

On `SKIP`, also set `status: deleted`, `status_updated_at`, `deleted_auto: true`, and `deleted_reason` by priority: `remoteOnly` fail → `wrong_location`; `compensation` fail → `compensation`; `roleType` fail → `role_mismatch`; `timezone` fail → `wrong_location`; skills/primary-stack fail → `missing_skills` (with `missing_skills` populated from required non-soft `DONT_HAVE` skills); anything else → `role_mismatch`. If `missing_skills` would be empty, fall back to `role_mismatch`, since the backend rejects that combination.

Rendered report, inserted above the job details:

```markdown
## Fit Evaluation

**PASS - 7/10** | required match 83% | overall 75%

<summary>

### Hard Screen
- Remote only - pass: "fully remote, US-based"
- Compensation - unclear: Not disclosed
...

### Skills
| Skill | Requirement | Tier | Status |
...

### Company, Location, Compensation
(evidence quotes, annualized max, hourly equivalent)
```

## Failure behavior

If both attempts fail validation, or `ANTHROPIC_API_KEY` is unset, write the note unscored with `fit_error: parse_failed` (or `no_api_key`) and leave `status: new`. This deviates from "skip the posting" in the spec: losing a captured posting to a transient model failure is worse than an unscored note you can spot by querying `fit_error`.

## Config and cost

- `ANTHROPIC_API_KEY` required; `WELLFOUND_SCORE_JOBS=0` disables scoring; `WELLFOUND_PROMPT_FILE` overrides the prompt path.
- Add `@anthropic-ai/sdk` and `zod` to [playwright/package.json](playwright/package.json).
- Scoring is sequential, matching the existing per-job loop. Roughly 3-6s added per job, so ~5-10 minutes over a 100-job run. Sequential calls also keep the 5-minute prompt cache warm.
- Estimated cost at ~2.9k cached system tokens, ~1.2k posting tokens, ~900 output tokens: about half a cent per job, under $1 for a full 100-job run.
